# Admissions integration coverage

Status describes the real Convex-backed journeys on `feat/member-admissions`. Local acceptance runs use an isolated Convex deployment and synthetic accounts. They do not write to live Google, Slack, IAM, or Resend services.

| Journey | Current evidence | Remaining verification |
| --- | --- | --- |
| Applicant identity and Midgard entry | Existing signed-in student sees the Midgard banner, opens the authenticated Hugin route, confirms or edits the existing profile, and profile edits update the existing student record. Missing-profile recovery links to Midgard `/profile`. Local browser journeys cover these paths. | Signed-out sign-in redirect across deployed apps and production identity-provider behavior. |
| Window, draft, and submission | Server mutations enforce the period window, ownership, revisions, and required consent. Applicant can save, submit once, reopen an eligible submission, and intentionally submit with no suitable suggested times. Hugin shows the closed state when no period is open. Browser clock tests verify that an already-open form and Midgard banner expire at the application deadline. | Explicit browser coverage for before-open and server rejection after-close; concurrent submission under real traffic. |
| Applicant privacy and board access | Applicant queries return only the caller's application; admin overview, calendar discovery, and schedule generation require admin access. Public offer/interview state is withheld until publication. Board notes are not included in applicant views. Backend authorization tests and real UI journeys cover key boundaries. | Broader adversarial testing across every query/action and deployed auth configuration. |
| Profile and consent | Hugin edits the existing student profile through its self-service mutation. Consent records its timestamp and version. Application retention is shown in the form; closing a period deletes admissions records while keeping the ordinary student profile and independent member account. | Verify policy wording and retention configuration with the data owner before production use. |
| Interview scheduling | Persistent Bifrost supports generated and manual schedules, selected calendars, rooms, interviewer teams, review, and publication. Backend tests cover two interviewers, availability, buffers, breaks, lunch, room/interviewer conflicts, pinned published slots, and cancelled interviews. Local browser coverage checks scheduling/publication and applicant cancellation. | Google Calendar API authorization, free/busy, event creation/cancellation, DST behavior, and provider failures against a controlled provider account. |
| Applicant cancellation and refill | An applicant can cancel an assigned interview. Cancellation always succeeds; the server reports refill eligibility only when at least 48 hours remain and never promises a replacement time. Published calendar cleanup and cancellation notices use retryable jobs. | Exercise real concurrent cancellation/refill and provider delivery failure in a controlled integration environment. |
| Decisions and offer response | Board decisions are separate from explicit send. Local browser coverage verifies rejection and replacement offer workflows. Applicant can accept or decline their own sent offer; declining creates no IAM account. Acceptance alone starts existing onboarding. Duplicate or stale responses are rejected. A server-side generic error prevents identity details from leaking if onboarding fails, with regression coverage. | Live IAM account linking, role preservation, Google/Slack provisioning and welcome delivery. No live provider write has been made. |
| Mail, reminders, and Slack | Email delivery is queued with idempotency and retry state. Local browser screenshots capture invitation, offer, and cancellation HTML where the flow produces it. Unit tests cover local email capture, delivery failure visibility, retryable alerts, delivery callbacks, and preserving delivery outcomes on retries. Rendered invitation/reminder tests verify room-map and Hugin links. Close queues channel archival after calendar cleanup and purges only after archival. | Live Resend delivery, invitation/reminder timing, provider callbacks, configured Slack workspace delivery/archive, and end-to-end failure recovery. Welcome-mail screenshots are not currently captured. |
| Close and retention | Close blocks new applicant access, queues cancellation of published calendar events, archives the period channel, then purges applications, notes, interviews, deliveries, outbox data, and the period in bounded batches. Admissions records are deleted; ordinary student profiles and independent member accounts are preserved. Lifecycle and recovery tests cover retries and ordering. | Operational confirmation of the retention policy and observation of provider cleanup in a controlled deployment. |

## Local acceptance commands

Run the local applications and isolated Convex deployment, then run the real student and board suites:

```sh
ADMISSIONS_SCREENSHOTS=1 pnpm exec playwright test e2e/admissions/student-production.spec.ts --project=student
ADMISSIONS_SCREENSHOTS=1 pnpm exec playwright test e2e/admissions/board-production.spec.ts e2e/admissions/board-workflow.spec.ts e2e/admissions/board-interviews.spec.ts e2e/admissions/board-settings.spec.ts --project=board
```

`student.spec.ts` and `board.spec.ts` remain explicitly local preview tests for Hugin and Bifrost. Real-flow screenshots use the `live-` prefix in [student](student.md) and [board](board.md). Captured email previews come from the local admissions delivery capture; they are not proof of external delivery.

Never capture credentials, tokens, or real applicant data. The production journey suite uses synthetic data seeded only into the isolated local Convex deployment.
