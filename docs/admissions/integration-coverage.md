Status reflects the current `feat/member-admissions` branch. “Planned” means production behavior and executable acceptance coverage are still required; it does not refer to a skipped or placeholder test.

| Journey | Status | Acceptance coverage still required |

## Existing implementation and reusable seams

- The Bifrost route mounts `AdmissionsPreview`; all candidate, schedule, decision, approval, send, and delete state is local React state backed by synthetic fixtures: [preview.tsx](../../apps/bifrost/src/components/admissions/preview.tsx), [model.ts](../../apps/bifrost/src/components/admissions/model.ts), and [model.test.ts](../../apps/bifrost/src/components/admissions/model.test.ts). The tests cover preview matching and availability rules, not production integrations.
- Product intent and constraints are recorded in [PRODUCT.md](../../apps/bifrost/PRODUCT.md). There are no admissions Convex modules/tables in the generated API or backend schema, and no Midgard admissions form/banner/query.
- The Midgard root layout and `PendingOfferBanner` provide an existing signed-in banner pattern: [layout.tsx](../../apps/midgard/src/app/layout.tsx), [pending-offer-banner.tsx](../../apps/midgard/src/components/common/pending-offer-banner.tsx). Applicant-owned data should be queried using the authenticated identity server-side.
- Reuse and test IAM through `api.iam.mutations.startOnboarding`, `iam/lifecycle.ts` (`activate`, `activateOnSignIn`), `iam/actions.ts` (`provision`, `linkSlack`), and `api.iam.mutations.retry`. The existing tests/fakes in `iam/onboarding.test.ts`, `test/iamFakes.ts`, and `test/fixtures.ts` cover existing identities, Google account reuse/provisioning, welcome delivery, and retry. `activate` grants `internal` only if no access role exists; preserve this role invariant. Role assignment precedes async Google/welcome completion, so test and document the intended accepted-membership state when provisioning fails rather than treating ordering alone as a defect.
- `iam/google.ts` uses the Google Workspace Admin Directory API only. No Calendar API/freebusy integration exists. Existing `convex/events/slack` lifecycle code can inform channel delivery/idempotency, but it is event-specific.
- Current Playwright preview coverage is in [student.spec.ts](../../e2e/admissions/student.spec.ts), [board.spec.ts](../../e2e/admissions/board.spec.ts), and [playwright.config.ts](../../playwright.config.ts), with scope documented in [COVERAGE.md](../../e2e/admissions/COVERAGE.md). It exercises Hugin and Bifrost local previews only; profile edits, submission, schedule approval, decisions, and delete remain in-memory simulations. Add executable integrated acceptance coverage as backend seams are implemented, using controlled Google Calendar/Slack/mail providers for failure and retry cases. Do not add empty skipped specs.

Never capture credentials, access tokens, private keys, or other secrets in screenshots or test artifacts. Use synthetic applicant data in visual evidence.

## Verification

On 2026-10-04, `pnpm exec vitest run convex/iam --coverage.enabled=false` from `packages/backend` passed: 11 test files and 106 tests. The IAM tests stub Google/Slack HTTP through `test/iamFakes.ts` or per-test `fetch` mocks; welcome mail is spied or handled by the test Resend component. No real external provider calls were made. This verifies the existing IAM onboarding, identity, linking, offboarding/reconciliation, provisioning retry, Google diagnostics, and Slack notification behavior. It does not verify an admissions acceptance trigger, because no admissions backend integration exists yet.
